# 15. 3Sum

## Quick Review

Sort the numbers, then fix one number at a time. For each fixed index `i`, search the remaining range with `left = i + 1` and `right = len(nums) - 1`:

- If the three-number sum is below zero, move `left` right.
- If the sum is above zero, move `right` left.
- If the sum is zero, save the triplet, move both pointers, then skip duplicate values.
- Skip an anchor that equals the previous anchor with `continue`; let the `for` loop advance `i` normally.

Sorting makes pointer movement predictable. The full scan takes `O(n²)` time after sorting, and the output may contain many triplets. The key discipline is to make progress after every match and to deduplicate without accidentally skipping a valid anchor.

## Problem

Given an integer array `nums`, return all unique triplets `[nums[i], nums[j], nums[k]]` such that `i`, `j`, and `k` are distinct indexes and the three values sum to zero.

The result must not contain duplicate triplets. The order of the triplets in the result does not matter.

Example:

```text
nums = [-1, 0, 1, 2, -1, -4]
result = [[-1, -1, 2], [-1, 0, 1]]
```

## The standard structure

This problem has two nested jobs:

1. The outer loop chooses an **anchor** value.
2. The inner two-pointer scan finds pairs in the remaining sorted suffix that sum to `-nums[i]`.

```text
sort nums

for each anchor index i:
    left = i + 1
    right = last index
    while left < right:
        compare nums[i] + nums[left] + nums[right] with 0
```

The outer loop explores possible first values. The inner loop must scan the whole remaining interval; one comparison per anchor is not enough.

## Recommended solution

```go
func threeSum(nums []int) [][]int {
	sort.Ints(nums)
	result := make([][]int, 0)

	for i := 0; i < len(nums)-2; i++ {
		if i > 0 && nums[i] == nums[i-1] {
			continue
		}

		left, right := i+1, len(nums)-1
		for left < right {
			sum := nums[i] + nums[left] + nums[right]

			switch {
			case sum < 0:
				left++
			case sum > 0:
				right--
			default:
				result = append(result, []int{nums[i], nums[left], nums[right]})

				left++
				right--
				for left < right && nums[left] == nums[left-1] {
					left++
				}
				for left < right && nums[right] == nums[right+1] {
					right--
				}
			}
		}
	}

	return result
}
```

This snippet requires `import "sort"`. Sorting changes the input slice. If the caller needs the original order preserved, make a copy before sorting.

## What went wrong while solving it

### 1. The inner pointers did not scan the interval

In an early version, `left` and `right` were initialized for an anchor, but the code checked only one pair instead of repeating while `left < right`.

That misses candidate pairs. The two-pointer technique is a traversal: after a sum comparison, one pointer moves, and the inner loop continues until the pointers meet. The outer loop chooses an anchor; the inner loop performs the full scan for that anchor.

### 2. Duplicate skipping did not guarantee progress

After finding a triplet, duplicate values were skipped in `while` loops, but the pointers were not first moved past the matched pair. If the pointer values did not change, the next iteration could see the same pair again. The loop condition remained true, the same triplet kept being appended, and memory usage grew until allocation failed.

The safe order is:

1. Save the triplet.
2. Move `left` once and `right` once.
3. Skip any further duplicates of the values just used.

This guarantees progress even when there are no duplicates. Every successful-match branch must move the search state forward.

### 3. The anchor index was incremented twice

The outer `for` loop already increments `i` after each iteration. Manually writing `i++` in the duplicate-anchor branch and then continuing causes an extra increment, which can skip an anchor and miss a valid triplet.

Use:

```go
if i > 0 && nums[i] == nums[i-1] {
	continue
}
```

`continue` transfers control to the loop’s normal step, which increments `i` once.

## Why the pointer moves are correct

The array is sorted. For a fixed anchor:

- If the sum is too small, keeping `left` and moving `right` left would make the sum no larger. Move `left` right to try a larger value.
- If the sum is too large, keeping `right` and moving `left` right would make the sum no smaller. Move `right` left to try a smaller value.
- If the sum is zero, record the triplet and move both pointers to search for a different pair.

The inner invariant is that any pair not yet ruled out lies between `left` and `right`. Each comparison either finds a result or discards at least one position, so the scan terminates.

## Deduplication rules

Deduplication happens at two levels:

| Level | Rule | Why |
| --- | --- | --- |
| Anchor | If `nums[i] == nums[i-1]`, use `continue`. | The earlier anchor already searched pairs for this same first value. |
| Pair after a match | Advance both pointers, then skip values equal to the values just used. | Reusing either value at the same position would produce the same triplet again. |

The practical idea is: **skip over equal values so the next search position points to a different value.** Do not let deduplication replace the required pointer movement.

## Correctness outline

After sorting, every value to the right of an index is at least as large as the value at that index. For each distinct anchor, the inward scan checks the possible pairs systematically:

1. A sum below zero rules out the current `left` with every remaining `right`.
2. A sum above zero rules out the current `right` with every remaining `left`.
3. A zero sum is recorded, and moving both pointers continues the search without reusing that exact pair.
4. Skipping duplicate anchors and matched pair values prevents repeated triplets without removing a distinct value combination.

Thus, every valid unique triplet is found once, and no invalid triplet is added.

## Complexity

- **Sorting:** `O(n log n)` time.
- **Search:** `O(n²)` time across all anchors.
- **Total time:** `O(n²)`, dominated by the search.
- **Extra space:** The algorithm itself uses `O(1)` auxiliary space apart from sorting implementation details and the returned result. The output space depends on the number of unique triplets.

## Edge cases

| Input | What to check |
| --- | --- |
| Fewer than three values | The outer loop does not run; return an empty result. |
| No triplet sums to zero | Return an empty result without inventing a triplet. |
| All values are zero | Return `[[0, 0, 0]]` exactly once. |
| Many repeated values | Duplicate anchors and matched pair values must be skipped. |
| Negative and positive values | Sorting allows the sum comparison to guide pointer movement. |
| Match with no duplicates nearby | The pointers must still move after appending the triplet. |

## Lessons from debugging

- **Initialize and traverse:** Setting `left` and `right` only defines the search range; the inner loop must keep moving through that range.
- **Every loop path must make progress:** In a successful-match branch, move both pointers before skipping additional duplicates.
- **Let loop syntax own the loop index:** In a stepped `for` loop, use `continue` to skip an iteration instead of incrementing the counter manually.
- **Deduplication means finding the next different value:** Skip equal values after the current choice, but do not skip the movement that leaves the current choice.
- **Trace a tiny example:** A short all-equal input makes repeated-result loops and missing pointer steps easy to spot.

## Interview answer template

> I’ll sort the array, then fix each distinct value as an anchor. For each anchor, I’ll use two pointers over the remaining suffix. If the sum is low, I move the left pointer to a larger value; if it is high, I move the right pointer to a smaller value. When the sum is zero, I record the triplet, advance both pointers, and skip duplicates. The outer loop plus the linear scan gives `O(n²)` time after sorting. I’ll also make sure every branch moves its pointers and that the loop itself advances the anchor exactly once.
